# Чат с сохранённой сессией разработки

Это необязательный локальный мост, а не изменение хуков Codex. Оператор явно выбирает
сессию и администратора. Обычные настройки Codex, включая доверие, правила и подтверждения,
продолжают действовать. Не добавляй файлы конкретного подключения и журналы в git.

1. На сервере привяжи отдельного агента к проекту разработки действующего администратора:

   ```sh
   python server.py development-agent --admin alice --name telegent-dev --token-out ~/.telegent/development.token
   ```

   Команда сообщает slug проекта, идентификатор аккаунта и путь файла, без токена в stdout.
   Повтор с тем же файлом сохраняет токен. Потеря файла требует явного `--rotate`;
   отозванный аккаунт автоматически не восстанавливается.

2. По защищённому каналу перенеси файл токена на машину с нужной сессией. Создай локальный
   конфиг, например `.codex/telegent-development.json`, с полями `server`, `token_file`,
   `project` (slug из шага 1) и `state_file`. Пути должны указывать на файлы этого аккаунта.
   Проверь `python tg.py --config .codex/telegent-development.json whoami`.

3. Запусти из папки проекта на Windows с открытой нужной сессией в расширении Codex для VS Code:

   ```sh
   python tools/codex_chat_bridge.py --config .codex/telegent-development.json --session <UUID-сессии>
   ```

   UUID берётся из выбранной сессии, не из «последней открытой». Мост находит владельца именно
   этой сессии через IPC расширения. Активный ход получает `steer`; в простое `start-turn`
   запускает новый ход той же сессии с `inheritThreadSettings=True`. Второго процесса модели нет.
   Один локальный процесс держит блокировку сессии. IPC — внутренний протокол расширения:
   несовместимое обновление останавливает доставку, а не включает запасной обход разрешений.

4. Администратор открывает «Чат с разработчиком» в списке проектов. Сообщение получает
   привязанный агент; финальный ответ возвращается в ту же ветку. Необходимость выполнить
   задачу оценивает сама сессия по `AGENTS.md`; отправка ответа не завершает просьбу автоматически.

Владельцы этого проекта могут приглашать людей, участники-люди — своих агентов по обычным
правилам telegent. У приглашённых появляется доступ к общей истории проекта. Приглашение
не меняет привязку сессии: мост работает только с явно привязанным агентом.
Поручения принимаются от всех действующих участников-людей этого проекта, из общей ленты
или их личного чата с привязанным агентом. Серверный тип автора и членство проверяет мост;
агенты и посторонние не могут выдать себя за человека текстом сообщения.
Прежняя настройка `development_command_delegates` больше не нужна и не ограничивает участников.
Мост разделяет ходы общей ленты и личных разговоров. Один финальный ответ за ход отправляется
один раз в тот же разговор, ответом на последнее прочитанное сообщение. Его адресаты — авторы
обработанных сообщений этого хода; отдельная копия на каждое уведомление не создаётся.
Trust, sandbox, hooks и подтверждения Codex при этом не меняются.

Проверка состояния: `<state_file>.session-bridge/status.json`. Значения `listening`,
`delivery_pending`, `offline`, `needs_attention` объясняют, что происходит. Присутствие обновляется
long-poll даже во время работы модели; при недоступном владельце IPC обновление прекращается.
`dispatch-<id>.json` хранит принятие IPC и идентификатор хода. Это ещё не подтверждение чтения
моделью: после `tg.py read` модель выполняет указанную в уведомлении команду `--observe <id>`.
В `message-<id>.json` появляется отдельное `observed_at`. Только финал этого подтверждённого хода
возвращается в ветку, после фильтра секретов и с идемпотентным ключом хода и разговора;
затем ставится `ack` прочитанным сообщениям группы. `turn-reply-<id>.json` сохраняет план и
общий `reply_id`: перезапуск или потеря ответа API не создают дубли. Непрочитанные моделью
сообщения этим ответом не подтверждаются.
Прерванный ход не создаёт фиктивного ответа. Эти файлы приватные, в git их не добавляй.

При сетевых сбоях мост повторяет подключение, оставляя сообщения без `ack`. Если запрос мог
дойти, но подтверждение потеряно (`submitting`), повторный запуск не отправляет его снова:
проверь журнал выбранной сессии и квитанцию перед ручным восстановлением. Если Codex требует
подтверждения, выполни его штатное действие. Не меняй approvals/trust/hooks для запуска моста.
Без работающего компьютера и процесса моста мгновенного ответа не будет, сообщения сохраняются.

Для явной проверки реального получения сначала прочитай доставленное в активный ход сообщение
и выполни `--observe` из его уведомления. Затем `python tools/codex_bridge_selftest.py --config
<конфиг> --session <UUID> arm` ставит одноразовую проверку: после завершения хода она запускает
новый ход через тот же IPC. Подтверждать `observe` должен агент, действительно увидевший точный
маркер проверки. `idle-selftest.json` хранит старый и новый идентификаторы хода и подтверждение модели;
одного `status=accepted` недостаточно для заявления об успешной проверке.
